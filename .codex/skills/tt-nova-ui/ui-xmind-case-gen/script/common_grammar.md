# 跨设备数据传递说明（Cross-Device Variable Passing）

## 背景说明

基于 AutoGLM 执行框架，多台设备由独立 agent 串联执行，**agent 之间无共享内存**。框架目前**不存在通用的跨设备公参格式**，只有以下白名单中的特定方式支持跨设备数据传递。

---

## 可用跨设备变量（白名单）

| 变量 | 语法 | 说明 | 典型用途 |
|------|------|------|---------|
| 设备当前登录账号的 UID | `<设备名.SYSTEM_GET_UID>` | 内联写入步骤文本，执行层自动替换为实际值 | 管理员授权、按 UID 操作指定用户 |
| 设备当前登录账号的昵称 | `${设备名.ai_data_gen_resp[nick_name]}` | 对应设备需先自行执行 `ai_get_nickname`，后续其他设备才能引用其昵称 | 按昵称定位 invite 目标、校验邀请弹窗中的邀请人昵称 |

> 不在此表中的数据类型**不支持跨设备传递**。如遇需要跨设备传值的新场景，需先确认框架新增了支持，再更新此表；不得自行推断或捏造引用语法。

### 使用示例

```markdown
##### **操作步骤**
${richText_690001010101:TT-主播设备-1} [auto] #<TT-主播设备-1.SYSTEM_GET_UID> 设置 <TT-非主播设备-2.SYSTEM_GET_UID> 为管理员;
```

执行时两处 `SYSTEM_GET_UID` 分别被替换为对应设备的实际 UID。

### 使用示例：先获取昵称，再跨设备引用

```markdown
#### **前置条件**
${richText_691001010102:TT-非主播设备-2} ${richText_401009:ai_get_nickname};

##### **操作步骤**
${richText_690001010101:TT-主播设备-1} [auto] 打开嘉宾邀请面板; 对昵称为 ${TT-非主播设备-2.ai_data_gen_resp[nick_name]} 的用户点击 `invite`;
```

上例中，`TT-非主播设备-2` 是**被获取昵称的一方**，必须先执行 `ai_get_nickname`；随后 `TT-主播设备-1` 才能通过 `${TT-非主播设备-2.ai_data_gen_resp[nick_name]}` 引用该昵称。

如果是 `role2` 需要确认或同意 `role1` 发起的邀请，则 `role1` 也应先执行 `ai_get_nickname`，再由 `role2` 通过 `${role1.ai_data_gen_resp[nick_name]}` 引用邀请人昵称。

## 黄金路径（Golden Paths）

高频场景的固定最优路径，**场景匹配时必须使用，不得绕行**：

| 场景 | 强制路径 |
|------|---------|
| 非主播设备进入指定主播的直播间 | step 中写 `enter_room role=TT-主播设备-N`（N 替换为实际设备编号） |

> 黄金路径是约束，不是建议。当且仅当场景明确匹配时才适用；无匹配时按通用规则处理。新增条目需经确认后才能加入此表。

---

## 使用场景

### enter_room 通过 role 字段进房

`enter_room` 通过 `role` 字段直接指定目标主播的设备名称进房，执行层自动定位直播间，**无需获取 room_id**。

⚠️ `role` 值必须与用例中实际的主播设备名称**严格一致**（如 `TT-主播设备-1`、`TT-主播设备-2`），写错设备名会导致进房失败。

```markdown
##### **操作步骤**
${richText_691001010101:TT-非主播设备-1} [auto] ${richText_401026:enter_room};
```

`enter_room` 对应的 `inputData` 中 `role` 字段填主播设备名称：

```json
[
  {"key": "room_id", "value": []},
  {"key": "uid",     "value": []},
  {"key": "role",    "value": ["TT-主播设备-1"]},
  {"key": "retry",   "value": []},
  {"key": "required","value": ["True"]}
]
```

---
执行层根据 `role` 值 `TT-主播设备-1` 自动找到该主播的直播间并进房。

## RichText 同步要求

1. 步骤中引用的工具必须以 RichText 结构出现在对应设备的前置条件或步骤中
2. `SYSTEM_GET_UID` 是框架内置指令，内联写入步骤文本，**不需要 RichText 条目**
3. `enter_room` 使用 `role` 字段进房，**不走跨设备变量引用**
4. 使用 `${设备名.ai_data_gen_resp[nick_name]}` 前，对应设备必须先执行 `ai_get_nickname`

---

## 多设备并行与执行顺序

**同一个 `**操作步骤**` 块内出现多个设备时默认并行**：渲染时每条设备行末尾追加 `**[parallel]**`，且 `[auto]` 只加在**第一台设备**行，其余设备行不再添加 `[auto]`。

```markdown
##### **操作步骤**
${richText_690001010101:TT-主播设备-1} [auto] 操作A; **[parallel]**;
${richText_691001010101:TT-非主播设备-1} 操作B; **[parallel]**;
```

当跨设备存在**先后依赖**（如设备 A 执行完才能让设备 B 进房），不要把依赖方塞进同一个并行块；应在前一个块给出 `**预期结果**` 作为同步点，把依赖方步骤放到**后一个 `**操作步骤**` 块**，以此表达先后顺序：

```markdown
##### **操作步骤**
${richText_690001010101:TT-主播设备-1} [auto] ${richText_1234:create_room};  (create_room为虚构方法，仅作举例)
###### **预期结果** ${richText_690001010101:TT-主播设备-1} 直播间创建成功并进入直播间
###### **操作步骤**
${richText_691001010101:TT-非主播设备-1} [auto] ${richText_401026:enter_room};   后执行，通过 role=TT-主播设备-1 自动定位
```
