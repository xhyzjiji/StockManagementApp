# UI Xmind Case Gen

## Trigger Conditions

Activate when:

- User provides a `spec.md` (generated by `ui-xmind-case-specify`) and asks for test cases
- User provides a `.md` file containing Chapter 7 "Raw Case Seeds" tables
- User asks to generate, optimize, or supplement UI automation test cases

**Do not activate** for greetings, chat, or unrelated questions.

## Architecture Overview

```
spec.md (Ch.7 Seeds) ──→ seed_parser ──→ Seed[] per Feature
                    │
                    ├──→ nav_builder ──→ Navigation chains (rule-based)
                    │
                    └──→ SEED_EXPAND_PROMPT + LLM ──→ cases JSON per Feature
                                                         │
                                    seed_assemble ◄──────┘
                                         │
                                    TestModel JSON
                                         │
                                      render ──→ standardized cases/richtext outputs
```

**Design principle**: spec.md 已包含结构化的 Feature 元数据、依赖关系、角色信息和 seed 表格。
LLM 唯一的职责是**步骤展开**（将 seed 的「核心操作」展开为 2~5 步可执行的 GUI 动作）。
导航链、角色映射、工具替换、渲染全部由规则引擎完成，无需 LLM。

## Unified Path Contract

- **正式 Markdown 产物**：
  - `<repo_root>/tt-nova/ui/business/{vc}/{module}/xmind/{ui_path}_cases.md`
  - `<repo_root>/tt-nova/ui/business/{vc}/{module}/xmind/{ui_path}_richtext.md`
- **临时中间产物**：
  - `<repo_root>/tt-nova/ui/tmp/{vc}/{module}/ui-xmind-case-gen/F-XX_prompt.txt`
  - `<repo_root>/tt-nova/ui/tmp/{vc}/{module}/ui-xmind-case-gen/F-XX_cases.json`
  - `<repo_root>/tt-nova/ui/tmp/{vc}/{module}/ui-xmind-case-gen/test_model.json`
  - `<repo_root>/tt-nova/ui/tmp/{vc}/{module}/ui-xmind-case-gen/violations.json`
  - `<repo_root>/tt-nova/ui/tmp/{vc}/{module}/ui-xmind-case-gen/repair_prompt.txt`
  - 其他 coverage / validation / debug 文件也统一放到同一 tmp 目录

## Workflow

### Step 1: Read spec and analyze seeds

Read the user-provided `spec.md` file, then run `seed-info` to understand the scope:

```bash
python3 .cursor/skills/ui-xmind-case-gen/script.py seed-info spec.md
```

Output example:

```json
{
  "total_seeds": 198,
  "features": [
    {
      "feature_id": "F-01",
      "feature_name": "...",
      "seed_count": 13,
      "depends_on": []
    },
    {
      "feature_id": "F-02",
      "feature_name": "...",
      "seed_count": 11,
      "depends_on": ["F-01"]
    }
  ]
}
```

### Step 1.5: Load business knowledge (accounts + routes)

根据业务线通过 `gdpa-cli run lark-docs` 从远程飞书文档加载账号配置和 UI 导航路径。此步在 `seed-prompt` 命令中自动执行，也可通过参数控制。

**自动推断**：不传 `--biz` 时，系统扫描 spec.md 内容的关键词自动匹配业务线（如检测到"送礼"→营收，"竞猜"→游戏）。

**显式指定**：用户可通过 `--biz` 参数强制指定业务线。

**降级策略**：若 `gdpa-cli run lark-docs` 拉取失败（网络/权限/会话问题），自动降级使用本地 `data/accounts.txt` 和 `data/ui_routes.txt`。

业务线索引配置在 `script/data/knowledge_index.json`，格式示例：

```json
{
  "business_lines": [
    {
      "id": "revenue",
      "name": "营收",
      "keywords": ["送礼", "礼物", "coin", "gift", "营收"],
      "accounts_doc": "https://bytedance.sg.larkoffice.com/docx/...",
      "routes_doc": "https://bytedance.sg.larkoffice.com/docx/..."
    }
  ],
  "default": "revenue"
}
```

扩展新业务线只需在此文件中添加一条 `business_lines` 记录，指向该业务线自己的飞书文档 URL；底层读取统一走 gdpa 的 `lark-docs`。

### Step 2: Generate seed expansion prompt (per Feature)

For each Feature, generate the lightweight LLM prompt:

```bash
python3 .cursor/skills/ui-xmind-case-gen/script.py seed-prompt spec.md F-01 \
  -o /abs/path/to/repo/tt-nova/ui/tmp/{vc}/{module}/ui-xmind-case-gen/F-01_prompt.txt
```

可选参数（业务线知识加载）：

| Parameter | Flag | Default | Description |
|-----------|------|---------|-------------|
| 业务线 | `--biz` | 自动推断 | 业务线 ID（revenue / game 等） |
| 飞书用户 | `--user` | None | 飞书用户名（如 huangyiran.dd），用于远程文档权限 |
| 设备空间 | `--space-id` | None | 设备角色映射空间分区（bits space_id 或其 project/dir id）。设备 richtext 绑定主要在 `render` 生效；涉及设备时若用户未指定须先反问 |

The prompt automatically includes:

- **Navigation chain** (rule-based, from dependency graph + ui_routes.txt)
- **Tool registry** (all available automation tools)
- **Device role mappings** (主播→TT-主播设备-1, 观众→TT-非主播设备-1, etc.)
- **Seed table** (this Feature's seeds from Ch.7)

Then call the LLM with the prompt content and save the response as
`/abs/path/to/repo/tt-nova/ui/tmp/{vc}/{module}/ui-xmind-case-gen/F-01_cases.json`.

**LLM output format** (strict JSON array):

```json
[
  {
    "title": "验证竞猜 Icon 在录屏开播预览页展示",
    "seed_id": "F01-S01",
    "preconditions": ["测试账号", "hint: 客户端 ≥ 38.0", "hint: 非 JP 地区"],
    "step_expected_pairs": [
      {
        "step": "TT-主播设备-1 在 TikTok 首页点击下方【+】按钮",
        "expected": []
      },
      { "step": "TT-主播设备-1 选择【直播】", "expected": [] },
      { "step": "TT-主播设备-1 选择【手机游戏】Tab", "expected": [] },
      {
        "step": "TT-主播设备-1 查看工具栏区域",
        "expected": ["竞猜 Icon 展示在排队工具 Icon 后方"]
      }
    ]
  }
]
```

**Seed → Case expansion rules** (enforced by prompt):

1. **Navigation chain**: 从 TikTok 首页出发，沿依赖链展开完整 GUI 路径
2. **Device prefix（仅多设备）**: **多设备**（≥2 台）用例每条 step 以设备占位符开头（TT-主播设备-1 / TT-非主播设备-1）；**单机（单设备）用例不写任何设备占位符前缀**，step / expected / preconditions 直接写动作与断言（单机无需指定角色）。
3. **Step expansion**: 核心操作展开为 2~5 步 GUI 动作（点击/输入/滑动/等待）
4. **Assertion mapping（每步都要有预期，不打平）**: 预期结果转为 expected 数组。**每一条 step 都必须配一个可观测的预期结果**（与原始 case 一致），不允许任何步骤 `expected` 为空；**禁止把多个步骤打平/合并成一个步骤**。
5. **Preconditions**: 只写工具名（`测试账号` / `ttmock_preset` / `Gecko 配置` / `环境名称` / `libra实验`，可带参数）。 **工具选型**：PPE/泳道→`环境名称 env=`；地区/语言/debug AB→`ttmock_preset`（`ab_settings`/`ab_settings_live`=JSON对象string，禁止`libra=`/`flight:`/数组）；Libra加实验→`libra实验`（`region`+`libra_id`+`group_id`；**仅当有 Libra 链接**且缺 `group_id` 时分别问实验组与对照组，正向挂实验组、对照/反向挂对照组，见 [`../references/libra-group-assignment.md`](../references/libra-group-assignment.md)）；Gecko Channel/Package→`Gecko 配置`。**测试账号是硬性前置条件**：账号封禁/造号/生日年龄态/国家/直播权限等账号构造必须写进 `preconditions` 的参数化 `测试账号`，绝不能写成 `step_expected_pairs` 的自然语言步骤。**🚫 hint 不会被执行——禁止用 hint 承载任何测试逻辑**；mock 结果/失败原因、实验或开关、版本/设备/地区切换、后端状态构造等若已有工具覆盖也必须写工具参数，只有工具完全覆盖不了的非账号前置才可写成 `step_expected_pairs` 的可执行步骤（每步带 `expected`）。

> **单机渲染约定（render 层自动处理）**：
> - 用例若只涉及一台设备（显式设备占位 ≤ 1），渲染时**不输出任何设备角色前缀**，Feature 也不输出「主要角色」行。
> - **trie 前缀合并（关键）**：同一 Feature 内的单机用例会先按「前置条件」分组，再按**步骤文本**合并成前缀树——多个用例共享相同前缀步骤时该前缀只渲染一次，分叉处生成多个**分支**（兄弟「操作步骤」节点），还原原始脑图「同一前序节点挂多个分支」的结构，**不会每条用例各自重复整段前缀**。每个节点累计其预期结果。多个分组时，分组标题用「Feature · 判别词」区分（判别词取前置条件 remark > 首条用例标题 > 首步动作），整组共有的区域标签（US/EU）挂到分组标题上。
> - **Feature 内单机/多设备混排也会合并（重要）**：渲染按设备数在 Feature **内部**拆分——单机用例（≤1 台）走 trie 合并、多设备用例（≥2 台，如跨端联动）逐条渲染。**即使一个 Feature 同时含单机与多设备用例，单机部分的重复前缀仍会被合并**，不会因为「整个 Feature 不是纯单机」而整体退化为逐条重复渲染。
>   - 为使前缀能正确合并，生成 `*_cases.json` 时必须满足两条（否则合并失败、退化成重复分支、用例数翻倍膨胀）：
>     1. **步骤原子化**：一个 `step` 只描述一个最小 GUI 动作，**禁止**用"并/然后/后/再"把多个动作压进一个 step（如 `底部切换到 Discover tab 并打开某类目视频`、`点击 Report video 并勾选第一个理由后提交`），否则复合步骤无法与其他用例的同名原子步骤合并。
>     2. **文本一致**：同一前序动作在不同用例里**逐字一致**（建议复用原始用例/脑图的节点原文），不要同义改写。
>   - 渲染层 `_trie_merge_key` 会容忍尾部标点 / 多余空格 / 中英文引号样式的差异做兜底归一化，但词序、用词、是否复合不在兜底范围内——仍需生成层保证原子化 + 文本一致。
> - 每个动作节点各自跟随自己的「预期结果」；纯上下文/导航节点（无断言、作为共享前缀根）可不带预期结果。
> - 不再输出 `**[priority]** / **[tag]**` 独立行（bits 导入器会把它当成空的预期结果节点，且优先级并不会生效）。
> - 多设备（≥2 台）用例保持原有按设备角色聚合 + 并行渲染逻辑不变（不做 trie 合并），并保留各自用例标题与 `**[tag]**`；仅当 Feature 存在多设备用例时才输出「主要角色」行。

**Executable quality constraints**:

1. 账号前置默认优先使用账号池，尤其是营收/送礼/评论等并行场景。
2. 使用账号池时必须同时给出 `pool_name` 和 `pool_id`；只有 `pool_name` 视为不合格产物。
3. 若账号池没有 tag 信息，最终渲染的 `tag_name_list` 必须留空数组 `[]`，禁止输出 `[""]`。
4. 若 skill 根据设备角色能推断出建议 tag（如主播设备建议 `HOST`），但知识库里未配置该 tag，render 阶段应提示用户确认是否补充，而不是静默写死。
4. `preconditions` 中禁止出现“请人工配置账号”“需要已登录观众账号”这类 remark。
5. `enter_room` 必须带 `role` / `uid` / `room_id` 至少一个参数。
6. 禁止保留 `{placeholder}`、`TODO`、`TBD`、`待补充` 以及“5条以上/200+字符”这类模糊描述到最终可执行用例中。
7. **测试账号必须是前置条件**：`preconditions` 仅放 `测试账号` / `ttmock_preset` / `Gecko 配置` / `环境名称` / `libra实验` 工具；账号相关的构造/设置/前置达成（封禁、造号、生日/年龄态、国家、直播权限等）必须通过参数化 `测试账号` 写在 `preconditions`，**不得**写成 `step_expected_pairs` 的自然语言步骤，也不得塞进 `hint:`。其他非账号前置若已有工具覆盖也必须写工具参数；只有工具完全覆盖不了的非账号前置才可写成可执行步骤并各带 `expected`。
8. **造数 + 测试账号**：当 seed/spec 要求通过造数构造账号（年龄、生日、国家、直播权限、新账号态等）时，必须在 `preconditions` 里写参数化 `测试账号`，不要把“通过造数将测试账号置为...”写成自然语言步骤。格式：`测试账号 use_pipe_account=true country=sg livePermission=false birthday=2007-03-13`。其中 `country`、`livePermission` 必填，`birthday` 可选；render 会转换为 `{"is_used_pipe_pool":"ttAcount","ttAccount":{"livePermission":false,"birthday":"2007-03-13","country":"sg"}}`。例如“置为 19 岁”按当前日期回推 19 年填 `birthday=2007-03-13`。

### 埋点需求（ByteIO）与埋点断言规则（强约束）

当 spec 第 7 章某 seed 带**第 5 列 `byteio_case_list`**（由 `ui-xmind-case-specify` 从
`ByteIOCaseInfo` 写入；也对应 `bits_regression_input.json` 的 `is_byteio_case=true`）时，
该 seed 即为**埋点需求**。埋点断言的绑定是**确定性的、由脚本自动完成，LLM 不参与**：

1. **`seed_parser` 读第 5 列** → `Seed.byteio_cases`。
2. **`seed-assemble` 确定性注入到「预期结果」节点**：对带 `byteio_cases` 的 seed（按 `seed_id`
   匹配 LLM 生成的 case），把 `et_checker_G20 byteio_case_list=[...]` 追加到该 case **断言步骤
   （最后一步）的 `expected` 文本末尾**——埋点校验属于**预期结果节点**（对应原始脑图 nodeType=13
   预期节点上挂的 ByteIO resource），**不是独立操作步骤**。例如：

   ```json
   {"step": "点击活动banner", "expected": ["banner_click；page_show et_checker_G20 byteio_case_list=[{\"ID\":\"...\",\"AppID\":1180,\"Region\":\"sg\"}]"]}
   ```

   渲染后该预期结果节点变成 `**预期结果** banner_click；page_show ${richText_401060:埋点校验}`。
3. **参数来源唯一**：`byteio_case_list` 直接取自 spec seed 的 `byteio_cases`（元素含
   `ID`/`Name`/`InvokeNum`/`AppID`/`Region`）——**LLM 从不复述该 ID**，从根上避免写错/漏参。
   因此 `seed-prompt` 生成的 seed 表会把埋点 seed 标注为「埋点断言由系统自动注入，勿自行编写」。
4. **render 阶段**：`apply_tool_skills` 把预期结果里内联的 `et_checker_G20` token 转成 richtext
   占位符（保留断言事件文本在前），`byteio_case_list` 解析进 inputData，产出
   `[{"key":"byteio_case_list","value":["<用例数组 JSON 字符串>"]}]`（`mentionId` 每次调用新生成，互不重复）。
5. **缺参数就反问用户**（对应 Step 4.5）：若 spec 标了埋点需求但 `byteio_case_list` 为空/缺失，
   render 会抛 `[MISSING_PARAMS] tool=et_checker_G20 missing=byteio_case_list ...`，此时按 Step 4.5 反问用户：

   ```
   **et_checker_G20 缺少必填参数：byteio_case_list**

   该用例被识别为埋点需求，但未取到 ByteIO 埋点用例列表。请提供埋点用例（可多条）：
   - **ID** - ByteIO 用例 ID
   - **Name** - 用例名称
   - **AppID** - 应用 ID（默认 1233）
   - **Region** - 区域（如 sg）

   示例：`et_checker_G20 byteio_case_list=[{"ID":"...","Name":"...","InvokeNum":1,"AppID":1233,"Region":"sg"}]`
   ```

### 地区（US / EU）与备注标记规则（强约束）

以下规则在生成阶段写入用例，render 阶段还会做一次确定性兜底（识别 → 补 ttmock_preset 地区 → 打 US/EU 标签 → remark 补 `<ttat>`），但**生成时就应主动满足**：

1. **us → ttmock 地区**：当 seed 提示要用到 us（入口状态 / 前置 / 标题出现「US」「美国」「US store region」等），**或所用账号名里包含 `us` 字样**时，前置条件**必须**写 `ttmock_preset region=US`，把地区设置成 us。需要 eu 时同理写 `ttmock_preset region=EU`。
2. **US / EU 根节点标签**：凡是命中 us 的用例，输出 JSON 的 `tags` 必须包含 `"US"`；命中 eu 的用例 `tags` 必须包含 `"EU"`。该标签会渲染到**用例（分支）根节点**（`### 标题 **[tag]** US`）。
3. **前置条件 remark 一律打 `<ttat>`**：所有节点前置条件里的备注（来自 `hint:` 或 `**[remark]**` / `**[note]**`）渲染后统一为 `**[remark]** <ttat> <说明>`。生成时正常写 `hint: <说明>` 即可，`<ttat>` 由 render 自动补齐，无需手写。
   - **前置条件节点恒带 `**[remark]** <ttat>`（强约束，render 自动保证）**：只要用例存在前置条件节点（无论内容是 `测试账号` / `ttmock_preset` / `Gecko 配置` 等工具占位还是备注），该节点渲染后**必须**含 `**[remark]** <ttat>` 标记。若用例本身没有任何 `hint:`/remark，render 会在前置条件行末尾自动追加一条空 body 的 `**[remark]** <ttat>`；若已有带说明的 remark（如 `**[remark]** <ttat> 本用例在 Android 设备验证`）则不再重复追加。生成层无需为此特意写空 hint。

### Step 2.5: Post-generation validation (mandatory)

After each feature's `*_cases.json` is generated, the skill agent **must** scan all cases and validate the following before proceeding to Step 3. **Do not skip this step.**

**A. Parameterized tool completeness check**

Scan every `preconditions` entry for parameterized tools and verify required params are present:

| Tool | Required Params | How to Extract |
|------|----------------|----------------|
| `libra实验` | `region=` + `libra_id=` + `group_id=` | **仅当有 Libra 链接时**：URL → `libra_id`（+ 尽量抽 `region`）；缺 `group_id` 分别问实验组与对照组，正向挂实验组、对照/反向挂对照组。无链接不套成对追问。禁止只问一个笼统 group、禁止把 flight 塞进 `ttmock_preset`。见 [`../references/libra-group-assignment.md`](../references/libra-group-assignment.md) |
| `open_schema` | `url=XXX` | From spec's navigation or entry point description |
| `mock_set_keva` | `repo=XXX keva=XXX` | From spec's mock configuration |

If any required param is missing or empty, **ask the user** before proceeding:
- Example: `libra实验 缺少 group_id。spec 有 flight/71789964，libra_id=71789964，region=sg。请分别提供：1) 实验组 group_id 2) 对照组 group_id（可贴版本表/截图）。正向 case 用实验组，对照/反向用对照组。`

**A2. `ttmock_preset` ab_settings JSON 对象自检（mandatory when present）**

若 `preconditions` 里写了 `ab_settings=` 或 `ab_settings_live=`，**必须**先把值抽出来，调用校验命令确认它是 **JSON 对象 string**（top-level 必须是 `{}`，不能是数组/非 JSON）。**有则必检，不可跳过**：

```bash
python script.py check-json-object --param ab_settings '<抽出的值>'
# 或: python -c "from script.tool_skills import is_json_object_string; print(is_json_object_string(r'''...'''))"
```

- 输出 `{"ok": true, ...}` → 通过
- 输出 `{"ok": false, "reason": "..."}` → **不要靠脚本改写**；根据用户/spec 意图把该字段重写成标准形态后重新生成该用例，例如：
  - ✅ `ttmock_preset ab_settings={"72192329":"1","72218451":"1"}`
  - ❌ `ab_settings=[{"key":"72192329","value":"1"}]`
  - ❌ `ab_settings=flight:72226837`
- render / md→xmind 转换若报 `[INVALID_JSON_OBJECT] tool=ttmock_preset param=ab_settings ...`，同样按上述标准格式重写后重跑；**有值但格式错会硬失败，不会静默清空**。

**A2. `ttmock_preset` ab_settings JSON 对象自检（mandatory when present）**

若 `preconditions` 里写了 `ab_settings=` 或 `ab_settings_live=`，**必须**先把值抽出来，调用校验命令确认它是 **JSON 对象 string**（top-level 必须是 `{}`，不能是数组/非 JSON）：

```bash
python script.py check-json-object --param ab_settings '<抽出的值>'
# 或: python -c "from script.tool_skills import is_json_object_string; print(is_json_object_string(r'''...'''))"
```

- 输出 `{"ok": true, ...}` → 通过
- 输出 `{"ok": false, "reason": "..."}` → **不要靠脚本改写**；根据用户/spec 意图把该字段重写成标准形态后重新生成该用例，例如：
  - ✅ `ttmock_preset ab_settings={"72192329":"1","72218451":"1"}`
  - ❌ `ab_settings=[{"key":"72192329","value":"1"}]`
  - ❌ `ab_settings=flight:72226837`
- render 若报 `[INVALID_JSON_OBJECT] tool=ttmock_preset param=ab_settings ...`，同样按上述标准格式重写后重跑，不要尝试兼容乱七八糟的自然语言缩写。

**B. Multi-device account uniqueness check**

For every case that involves 2+ devices:
1. Collect all `测试账号` entries from preconditions
2. Verify host-device and viewer-device use **different** accounts:
   - If using `phone_number=X` — the phone numbers must differ
   - If using `pool_name=X` without phone_number — acceptable (pool auto-allocates)
   - If both devices use bare `测试账号` with no params — **FAIL**: they may get the same account
3. On failure, fix by assigning appropriate fixed accounts (host → role=host account, viewer → role=viewer account)

**C. Account-scenario matching check**

Verify the selected accounts match the test scenario:
- Gift/revenue scenarios → must use "送礼场景" fixed accounts, not game pool
- Game live scenarios → must use GameLiveOpen pool
- If mismatch detected, fix the preconditions before assembly

**D. 埋点需求（ByteIO）绑定检查**

For every source case/seed marked as 埋点需求（`is_byteio_case=true` / non-empty `byteio_cases`）:
1. 确认生成的用例里，对应断言步骤已绑定 `et_checker_G20 byteio_case_list=<...>` 埋点断言。
2. 确认 `byteio_case_list` 的用例元素与源 `byteio_cases` 一致（`ID`/`Name`/`AppID`/`Region`），未被改写或臆造。
3. 若源标记为埋点需求但取不到用例列表，**ask the user**（见「埋点需求」小节的反问模板），拿到后再补参数。

Merge all features' cases into a single TestModel:

```bash
python3 .cursor/skills/ui-xmind-case-gen/script.py seed-assemble spec.md \
  --cases F-01=/abs/path/to/repo/tt-nova/ui/tmp/{vc}/{module}/ui-xmind-case-gen/F-01_cases.json \
          F-02=/abs/path/to/repo/tt-nova/ui/tmp/{vc}/{module}/ui-xmind-case-gen/F-02_cases.json \
          F-03=/abs/path/to/repo/tt-nova/ui/tmp/{vc}/{module}/ui-xmind-case-gen/F-03_cases.json \
  -o /abs/path/to/repo/tt-nova/ui/tmp/{vc}/{module}/ui-xmind-case-gen/test_model.json
```

The `seed-assemble` command automatically extracts from spec.md:

- Module name
- Feature names and primary roles
- Feature relationships (dependency graph)

### Step 3.5: 确认设备空间分区（space_id，涉及设备时必做）

设备角色（`TT-主播设备-n` / `TT-非主播设备-n`）的 richtext `pluginData.id` 按 **bits 空间（space_id）** 分区——同一设备枚举在不同空间下对应不同的平台插件实例 id。因此：

- **只要用例涉及使用设备**（多设备/多角色，或前置/步骤里出现设备占位符），渲染前**必须**确定 `space_id`。
- **若用户没有指定空间 id，必须先反问用户**（例如：「本次用例涉及设备占位，请提供目标 bits 空间 id（space_id），或其下的 project/dir id，用于绑定正确的设备插件实例」），拿到后再继续。
- 已内置分区：目前只有 `default`；未知空间一律回退 `default`。
- 内置 id 是快照，平台重建角色后会漂移；**权威来源是 `POST bits-cn-gw.bytedance.net/test_case/role/list`**（`bits_space_id`）。上传脚本会在写 bits 前自动比对，对不上直接报错。发现漂移时按平台返回值改 `device_role_skills.py`，不要凭印象新增分区。
- 通过 `--space-id` 传给 `render`（也可传给 `seed-prompt`）。
- **纯单机、完全不涉及设备占位的用例**可不传 `--space-id`（不影响 markdown 占位符，只影响设备 richtext 绑定）。

### Step 4: Render to output files

```bash
python3 .cursor/skills/ui-xmind-case-gen/script.py render \
  /abs/path/to/repo/tt-nova/ui/tmp/{vc}/{module}/ui-xmind-case-gen/test_model.json \
  --space-id <space_id>  # 涉及设备时必填；未提供须先反问用户 \
  --cases-output /abs/path/to/repo/tt-nova/ui/business/{vc}/{module}/xmind/{ui_path}_cases.md \
  --richtext-output /abs/path/to/repo/tt-nova/ui/business/{vc}/{module}/xmind/{ui_path}_richtext.md
```

The render pipeline:

0. **地区识别与兜底（US / EU）**: 识别用例是否涉及 us/eu（账号名含 us/eu、`region=` 参数、标题/前置出现 US/EU/美国/欧盟）。命中则补 `ttmock_preset region=US|EU` 前置，并给用例根节点打 `US` / `EU` 标签。
1. **Tool skill matching**: free-text preconditions → `${richText_uuid:tool_name}` placeholders；前置条件里的备注统一渲染为 `**[remark]** <ttat> <说明>`。
   - **Hard constraint — unique `mentionId` per tool call**: 每一次工具调用（含同工具、相同 inputData 的多次调用）都必须生成**全新且互不重复**的 `mentionId`（以及对应的 richtext `uuid`）。禁止复用 `TOOL_SKILLS` 注册表里的静态 `mention_id`，也禁止按 inputData 去重共用。工具身份靠 `saitamaTemplateId`，实例身份靠每次新生成的 `mentionId`。
2. **Role-aware rendering**: steps grouped by device (one parallel lane per device). Multi-device step blocks append `**[parallel]**` to every device line; the `[auto]` marker is added only to the **first device** line. 设备 richtext 的 `pluginData.id` 取决于 `--space-id`。US / EU 等用例标签直接挂在用例标题（分支根节点）上：`### 标题 **[tag]** US`。
3. **RichText extraction**: list of all richtext bindings（按调用实例列出；同工具多次调用会出现多条不同 `mentionId` 的条目）

**If render fails with `[MISSING_PARAMS]`**:

The command will exit with code 2 and output a structured error line:
```
[MISSING_PARAMS] tool=libra experiment missing=region,libra_id,group_id hint=region=区域代码(如sg/us/jp)；libra_id=实验ID；group_id=分组ID；libra_title=实验标题(可选)
```

When you see this, **follow Step 4.5** to interact with the user.

**If render fails with `[INVALID_JSON_OBJECT]`** (e.g. bad `ttmock_preset` `ab_settings`):

```
[INVALID_JSON_OBJECT] tool=ttmock_preset param=ab_settings reason=json_array_not_object hint=必须是 JSON 对象字符串... raw=[...]
```

Do **not** invent compatibility rewrites. Fix the case JSON so the param is a standard JSON object string (e.g. `{"72192329":"1"}`), optionally verify with `python script.py check-json-object`, then re-render.

Output:

- **`tt-nova/ui/business/{vc}/{module}/xmind/{ui_path}_cases.md`** — Structured test cases in Markdown
- **`tt-nova/ui/business/{vc}/{module}/xmind/{ui_path}_richtext.md`** — RichText list JSON for platform tool/device bindings

### Step 4.5: Missing required tool params → ask user interactively

If render command reports a missing required tool param (for example:

- `[MISSING_PARAMS] tool=open_schema missing=url hint=Input必填。url=Required；validation_str=Optional。`
- `[MISSING_PARAMS] tool=mock_set_keva missing=repo,keva hint=Input必填。repo=Required；keva=Required。`
  ), **do not stop at the CLI error**.

You must convert that failure into an interactive follow-up:

1. Identify the failing tool name and missing param names from the error message.
2. **Directly output a prompt in chat** (not via AskUserQuestion) with clear parameter instructions.
3. Explain which tool is blocked, what value format is needed, and list available options for enum-like fields.
4. After the user replies, patch the affected case JSON (or regenerate the affected feature cases) with the supplied params.
5. Re-run the blocked command and continue the pipeline.

If render command reports an account-pool tag suggestion, for example:

- `[SUGGEST_TAG] tool=测试账号 pool_name=Live-Revenue-Gift-UIAuto suggested_tag=HOST hint=账号池 ...`

you must ask the user directly:

> 检测到账号池 `Live-Revenue-Gift-UIAuto` 当前未配置 tag，但根据设备角色建议补充 `HOST`。是否需要我为这批用例显式加上 `tag_name_list=["HOST"]`？

If the user confirms, patch the affected `测试账号` 前置条件为显式带上 `tag_name_list=HOST`（或重新生成对应 cases），然后重新 render。

**Important**:

- This interaction belongs in the **skill/runtime layer**, not inside Python scripts.
- Keep Python validation strict; the skill should handle the conversation.
- Do **not** silently invent placeholder values.
- Do **not** automatically downgrade the tool to `hint` unless the user explicitly asks for that fallback.

**Recommended prompt style (direct chat output, NOT AskUserQuestion)**:

```
**{tool_name} 缺少必填参数：{param1}, {param2}, ...**

请直接回复参数值：
- **param1** - 参数说明
- **param2** - 参数说明（可选值：a / b / c）

示例：`{tool_name} param1=xxx param2=xxx`
```

Example for libra experiment:
```
**libra实验 缺少必填参数：region, libra_id, group_id**

请直接回复参数值：
- **region** - 区域代码（如 sg/us/jp）
- **libra_id** - 实验 ID
- **实验组 group_id** 与 **对照组 group_id**（必须成对；不要只给一个）
- **libra_title** - 实验标题（可选）

分配：正向用例 → 实验组；对照/反向用例 → 对照组。规范见 `references/libra-group-assignment.md`。

示例：`libra实验 region=sg libra_id=71315741 group_id=<按用例极性选实验组或对照组>`
```


**Why NOT use AskUserQuestion with preset options**:

- AskUserQuestion's "Other" option triggers "User declined to answer questions"
- Preset options like "手动输入参数" are interpreted as user declining the question
- Direct chat prompt allows natural user input without confusion
